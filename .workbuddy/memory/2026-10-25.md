# 2026-10-25 — rothko (K70U) UEFI 显示攻坚

## 结论：16→21 号镜像 33 秒复位的真凶定位

- 排除 GIC：原厂 DTB `interrupt-controller@c400000` 的 `reg` 是两条
  `0C400000+40000` / `0C440000+200000`，GICR 实际 2.25 MiB（`0C400000..0C640000`），
  8 核只需 1 MiB；20 号已把窗口扩到 16 MiB 仍 33 秒 → 重分布器扫描不是原因。
- 排除早期页表重设：21 号 `PcdRemapUnusedMemoryNx=FALSE` + `MEMORY_PROTECTION=FALSE`
  仍 33 秒。
- 纠正关键推理错误：`pc` 落在 `ArmCpuDxe` 的 `CpuDeadLoop` **不等于**故障在
  `ArmCpuDxe`——那是全局向量表所在模块，任何模块的同步异常都落到这里。
  反证：16 号有 `PcdFrameBufferDelay=10000` 的 10 ms/行延时，说明 GOP 已经装好，
  即 `RothkoDisplayDxe` 已跑通 → 故障在「装好 GOP 之后」（BDS 接控制台 /
  GraphicsConsole 画字 / 1 s 周期 `Refresh()`）。
- ATF dump 只给 `pc/lr/sp/pstate`（`esr_el2=0x5e000000` 是 SMC 残留，勿误读），
  拿不到 ESR/ELR/FAR。

## 22 号上机实测（14:19 adb 抓 expdb）

```
cpu(0) pc:<0000000043784d5c> lr:<2500fffffffffff1> sp:<000000004223ead0> pstate=20003c4
```

## 26 号：一次性修法（2026-10-25 15:13）

根因定性：`9` 是被截断成 32 位的 `EFI_OUT_OF_RESOURCES(0x8000000000000009)`，落进
64 位指针槽；BDS 控制台连接路径（`BmConsole.c!BmGetGopDevicePath`）有真实双重释放。

新增 `patches/0003-rothko-pool-hardening.patch`（`scripts/make-hardening-patch.py` 生成）：
1. `Pool.c!CoreFreePool`：拒绝 `Buffer < 0x1000` 或非 8 字节对齐的指针 → 返回
   `EFI_INVALID_PARAMETER`（反汇编核实在 DxeCore RVA 0x7f40）。**这一条就让 33 秒死循环消失**。
2. `BmConsole.c`：释放后置 NULL，删掉尾部重复释放（原来还会把正要返回的 GopPool 释放掉）。
3. `GraphicsConsole.c:1255`：`LineBuffer` 释放后置 NULL。
4. `RothkoDisplayDxe.c!Blt`：加 FrameBufferSize 边界校验，超窗返回错误而不是打野 cache。

镜像：`bringup/boot-rothko-uefi-26-hardened.img`，sha256 `18ee0fbf…e035`，307,200 B。
注意：被 0003 命中的 3 个 EDK2 文件本机原本是 CRLF，已 sed 成 LF（否则 LF 补丁不匹配）。
v4 信标保留作被动兜底（RVA 0x4e24 自旋）。

## dali 对照 + 29 号（16:07）

- dali（Redmi K80 Ultra / MT6991）实现在 `localhosts-A/UEFI-Dali`，已拉到 `D:/tmp/dali/`；
  核心 `Platforms/Xiaomi/daliPkg/Drivers/DisplayDxe/DisplayDxe.c`（12.7KB）。
  **注意：设备是 Redmi，小米不开源 MT6989 显示码，SoC 寄存器一律以 OnePlus MT6989
  开源码为准**（`src/OnePlusOSS-mt6989/.../mediatek_v2/`），dali 只当 UEFI 写法参照。
- OnePlus 源码坐实：mutex EN/MOD/SOF/MOD2 = 0x20/0x30/0x2C/0x34（MT6983 布局，
  mt6989 复用）；`MT6989_MUTEX1_MOD0_DISP_DSI0 = BIT(15)`；`DSI_MODE_CTRL=0x14`；
  **`mtk_dsi_start()` = writel(0); writel(1); 停在 1**（CPU 路径，CMD/VDO 通用）。
  我们的 mutex 偏移和 DSI0 位本来就对；抄错的是 DSI_START 三拍（0→1→0 是 GCE
  原子回放用的，CPU 重放会掐断传输）。
- 29 号 `boot-rothko-uefi-29-dali-align.img`（sha256 `eab2052e…fb4a`）：
  ① PushFrame 改 `mtk_dsi_start` 语义（0→1 停住，不写 CMDQ）；
  ② 提交前查 `DSI_MODE_CTRL & 3 == 0`（命令模式）；
  ③ 硬要求有扫描层地址 == fb base，否则拒绝推帧；
  ④ pitch 仍从 OVL 回读（rothko 1220 宽、硬件 pitch 1248px=4992B，不能照 dali 的 width*4）。
- 复位性质（27 号 expdb）：`kedump: last is full pmic reset!` = PMIC 全复位；
  28 号（不碰显示 MMIO）仍复位 → 复位源不在显示驱动；电源键长按已排除
  (`Long Pressed Reboot=0`)。dali 用 `DiagnosticBdsDxe` 画诊断页（GOP Blt 彩条 +
  SimpleTextOut 文字 + 按键），可作后续参照。

## 30 号：HALT 死循环是 15 秒 PMIC 复位根因（16:25）

`ROTHKO_HALT` 是 `b .` 死循环。StartRefresh 任一步失败 → 死循环 → PMIC 看门狗
~15s → PMIC 全复位（无 dump）。解释了 logo+15s 复位+无 AEE 三件事。

30 号 `boot-rothko-uefi-30-nohalt.img`（sha256 `bc10d523…cd23`）：
1. HALT 改 DEBUG_ERROR + return（不再 b .）← 让 15s 复位消失的关键
2. CMD 模式检查降级为警告（VDO 也推）
3. 补 mutex bank 0x14020000（DTB 有 5 个）
4. mutex 识别改 DSI0+OVL 双条件
5. StartRefresh 失败 → return（GOP 保留）

dali 关键差异已全部对齐：镜像到所有 scanout、DSI_START 0→1 停住、不写 CMDQ、
模式检查非致命。剩余问题（若仍 logo）只在 OVL→DSC→DSI 推帧路由。

## 30 号实测 + 31 号保活（16:27-16:35）

30 号：HALT 死循环去掉后 expdb **零崩溃记录**，但 15 秒复位仍在。
最后一次启动 RGU：`g_rgu_status=0x2`（软件看门狗）、`kedump: NOT full pmic reset`、
`exp_type=0x0`。复位性质 = RGU 软件 WDT（dual mode 二次超时），不是 PMIC。
我们的 `WDT_MODE` 直写没关掉它。

31 号 `boot-rothko-uefi-31-wdtkeep.img`（sha256 `deb0a5e9…8ca9`）：
1. 读-改-写关 EN（`(read & ~BIT0) | KEY`），再 RESTART 锁存
2. 独立 1s 定时器踢 `WDT_RESTART`（不依赖 StartRefresh）
3. 心跳写 `NONRST_REG = 0x40000000 | 秒数`，下次 preloader 自报存活时间

判据：NONRST_REG 非零→心跳在跑，WDT 不是 RGU；为 0→驱动没跑到入口。
